# Отчёт по практической №1 — локальный Lakehouse

## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | Степанова Полина Владимировна|
| Вариант (запрос) | **3 — Q18 «Large Volume Customer»** |
| Масштаб `sfN` | **sf1** (customer 150 000, orders 1 500 000, lineitem 6 001 215 строк) |
| Почему выбран такой масштаб | Машина — MacBook, Docker-VM на 8 ГБ, Trino одноузловой с heap 3,5 ГБ. На sf1 lineitem даёт 6 млн строк (~750 МБ «плоских» данных): этого достаточно, чтобы разница кодеков читалась в сотнях мегабайт и десятках секунд, а не в шуме замера, и при этом полный прогон лабы вместе с 12 комбинациями формат×кодек укладывается примерно в полчаса. На sf10 бенчмарк из 12 таблиц занял бы ~15 ГБ в MinIO и не поместился бы в память одного узла без перенастройки spill. Данные `tpch.sfN` детерминированы, поэтому витрина сверяется с эталонным Q18 (см. §3). Масштаб одинаковый на всех слоях. |

## 2. Поднятые сервисы — и почему именно они

Фактическое состояние (`docker compose ps`): 4 постоянных контейнера + 2 профильных, которые
запускаются по требованию.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| **MinIO** (`pgsty/silo`) | S3-совместимое объектное хранилище: сюда физически падают parquet/orc-файлы всех трёх слоёв (бакеты `bronze`, `silver`, `gold`) | Нужно было именно **S3 API**, а не диск: хранение отделяется от вычислений, движок можно выключить или заменить, не трогая данные, а код пайплайна потом переносится в AWS S3 сменой endpoint. Альтернатива «папка на диске» этого не даёт: нет единого протокола для нескольких движков и нет presigned-доступа. Официальные образы `minio/minio` больше не раздаются свободно, `quay.io/minio/aistor` требует лицензию — поэтому взят свободный форк Silo с теми же портами, переменными и консолью, без лицензии |
| **PostgreSQL 17** | БД, где Lakekeeper хранит метаданные каталога (таблицы, снапшоты, схемы) | Коммит снапшота Iceberg обязан быть атомарным, иначе две параллельные записи разрушат таблицу. Postgres даёт транзакции и уникальные ограничения «из коробки». Вариант «каталог в файле на S3» (hadoop-catalog) отброшен: у объектного хранилища нет атомарного compare-and-swap, это известный источник потери снапшотов |
| **Lakekeeper** | Iceberg **REST Catalog**: единый реестр таблиц для всех движков | REST Catalog — открытый протокол Iceberg, поэтому Trino и Spark видят одну и ту же таблицу в одном состоянии (проверено в §6.2: Spark читает Bronze, созданный Trino). Альтернативы: AWS Glue — облако и вендор-лок; Hive Metastore — лишний Thrift-сервис и своя БД, по сути тот же Postgres, но с устаревшим протоколом. Lakekeeper ставится одним контейнером и имеет UI |
| **Trino 476** | SQL-движок: ходит в Lakekeeper за метаданными, читает/пишет данные в MinIO | Три причины: (1) встроенный коннектор **`tpch`** — генератор данных варианта, ничего не нужно скачивать; (2) один движок умеет писать PARQUET, ORC и AVRO с кодеками NONE/SNAPPY/GZIP/ZSTD/LZ4 — весь бенчмарк §5 делается сменой одной session-переменной, без переписывания пайплайна; (3) MPP-движок без собственного хранилища, то есть отвечает только за вычисления. Spark как основной движок был бы тяжелее для интерактивного SQL, а ClickHouse не умеет писать Iceberg через REST-каталог |
| **Apache Spark 3.5.6** (профильный, часть 2 п.6.2) | Второй движок поверх того же каталога; читает Bronze напрямую из MinIO | Выбран вместо BI-инструмента осознанно — см. §6.2 |
| **`mc`** (профильный) | Клиент MinIO: создание бакетов, подсчёт объёма | Те же действия, что кнопками в UI, но скриптом — значит, воспроизводимо |

### Скрипты, которыми поднимала стек

Весь стек описан в `docker-compose.yml` и поднимается одним `./scripts/up.sh`. Compose выбран
вместо серии `docker run`, потому что сервисам нужна общая сеть: Lakekeeper и Trino должны
обращаться к MinIO по имени `minio:9000` изнутри сети (а не через `host.docker.internal`),
и порядок запуска задаётся healthcheck'ами, а не ручными паузами.

```bash
./scripts/up.sh
# 1/7  docker compose up -d minio pg        — хранилище и БД каталога
# 2/7  ждём pg_isready                      — Lakekeeper без живого Postgres падает на старте
# 3/7  ждём /minio/health/live
# 4/7  mc mb bronze silver gold             — три бакета, по одному на слой медальона
# 5/7  docker compose run --rm lakekeeper migrate  — одноразовые миграции схемы каталога
#      docker compose up -d lakekeeper serve
# 6/7  POST /management/v1/bootstrap        — принять Terms of Use (204)
#      POST /management/v1/warehouse ×3     — warehouse bronze/silver/gold (201 Created)
# 7/7  docker compose up -d trino           — Trino с каталогами bronze/silver/gold/tpch
```

Ключевые фрагменты `docker-compose.yml`:

```yaml
  minio:                       # S3-хранилище; 9000 на хосте был занят -> проброшен 9100/9101
    image: pgsty/silo:latest
    command: server /data --console-address ":9001"
    ports: ["9100:9000", "9101:9001"]
    volumes: [minio-data:/data]

  pg:                          # метаданные Lakekeeper; healthcheck гарантирует порядок старта
    image: postgres:17
    healthcheck: {test: ["CMD-SHELL", "pg_isready -U postgres"], interval: 3s, retries: 20}

  lakekeeper:                  # Iceberg REST Catalog
    image: quay.io/lakekeeper/catalog:latest-main
    command: serve
    environment:
      LAKEKEEPER__PG_DATABASE_URL_WRITE: "postgresql://postgres:postgres@pg:5432/postgres"
    depends_on: {pg: {condition: service_healthy}}

  trino:                       # SQL-движок
    image: trinodb/trino:476
    mem_limit: 5g              # без лимита JVM берёт 80% ОЗУ Docker-VM и контейнер убивает OOM
    volumes:
      - ./catalog:/etc/trino/catalog          # bronze/silver/gold/tpch
      - ./etc/jvm.config:/etc/trino/jvm.config:ro
      - ./etc/config.properties:/etc/trino/config.properties:ro
```

Отдельно про память: первый прогон Bronze убил контейнер Trino (`exit 137`, `OOMKilled`) на
записи lineitem. Причина — в образе стоит `-XX:MaxRAMPercentage=80`, и без `mem_limit` JVM
взяла 80% от всей 8-ГБ Docker-VM. Лечится явным конфигом (`etc/jvm.config`, `etc/config.properties`):
`-Xmx3500M`, `query.max-memory-per-node=1500MB`, `memory.heap-headroom-per-node=800MB`,
`task.max-writer-count=2`. После этого Bronze (7,65 млн строк суммарно) пишется за 42 секунды.

## 3. Разбор запроса — какие данные нужны

Вариант 3, Q18 «Large Volume Customer»: *клиенты и их заказы, в которых суммарное количество
товара больше 300; топ-100 по сумме заказа.*

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает |
|---|---|---|
| `lineitem` | `orderkey`, `quantity` | **Подзапрос**: `GROUP BY orderkey HAVING sum(quantity) > 300` — отбирает «крупные» заказы. Затем **джойн** с `orders` по `orderkey` и **агрегат** `sum(quantity)` в выводе. Самая тяжёлая часть: 6 001 215 строк читаются целиком |
| `orders` | `orderkey`, `custkey`, `orderdate`, `totalprice` | **Джойн** с `lineitem` (по `orderkey`) и с `customer` (по `custkey`); `totalprice` и `orderdate` идут в **сортировку** `ORDER BY totalprice DESC, orderdate` и в **вывод** |
| `customer` | `custkey`, `name` | **Джойн** с `orders` по `custkey`; `name` — в **вывод** |

Колонки `partkey`, `suppkey`, `discount`, `shipdate` и прочие запросу не нужны — они остаются
только в Bronze (слой обязан хранить источник как есть) и отсекаются на Silver.

Итог запроса на sf1 — **57 строк** (порог `quantity > 300` выполняется редко), хотя `LIMIT` равен 100.

**Проверка корректности.** `sql/04_validate.sql` сравнивает витрину Gold с эталонным Q18,
выполненным напрямую по `tpch.sf1`:

```
gold_rows  ref_rows  mismatched_rows
57         57        0
```

Витрина, собранная через три слоя, совпадает с эталоном строка-в-строку. Первая строка —
`Customer#000128120`, заказ `4722021`, `totalprice = 544089.09`, `total_quantity = 323`.

## 4. Медальон — решения по каждому слою

Замеры размеров получены скриптом `./scripts/stats.sh` — это физические байты из метаданных
Iceberg (`sum(file_size_in_bytes)` по таблице `"<table>$files"`), а не оценка планировщика.
Кодек задаётся session-свойством `<catalog>.compression_codec` на момент записи, поэтому в
`SHOW CREATE TABLE` его не видно — он указан в таблицах ниже.

### Bronze (сырой)

Бакет `bronze`. Принцип слоя: **все колонки источника, никаких фильтров**, только append.
Единственное добавление — техническая колонка `loaded_at` (метка загрузки): без неё на Silver
невозможен SCD Type 2 и аудит происхождения строки.

| Таблица | Колонки (что осталось) | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| `bronze.lakehouse.raw_customer` | все 8 колонок TPC-H + `loaded_at` | 150 000 | 7,84 (1 файл) | PARQUET | ZSTD | нет | 7,84 МБ в одном файле. Партиционирование здесь дало бы только мелкие файлы и лишние метаданные, а запросу нужен весь справочник целиком |
| `bronze.lakehouse.raw_orders` | все 9 колонок + `loaded_at` | 1 500 000 | 35,69 (7 файлов) | PARQUET | ZSTD | `year(orderdate)` | 7 естественных партиций (1992–1998), ровно по файлу на год. Любой фильтр по периоду отсекает файлы по метаданным, не читая их. Это единственная таблица, где у аналитики реально есть предикат по дате |
| `bronze.lakehouse.raw_lineitem` | все 16 колонок + `loaded_at` | 6 001 215 | 144,91 (2 файла) | PARQUET | ZSTD | **нет (осознанно)** | Q18 агрегирует lineitem **целиком**: фильтра по дате в запросе нет, значит partition pruning не сработал бы ни разу, а партиции по `year(shipdate)` добавили бы файлов, метаданных и времени записи. Вместо партиций работает column pruning: `agg1` читает 2 колонки из 17 |

Bronze целиком: **7 651 215 строк, 188,4 МБ** (без бенчмарочных таблиц).

### Silver (очищенный)

Бакет `silver`. Что делает слой: чистка (отбрасываем `NULL`-ключи, неположительные
`quantity`/`totalprice`), нормализация (`trim` строковых полей), обогащение (история версий
клиента) и сужение до колонок, нужных запросу.

| Таблица | Колонки (что осталось) | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| `silver.lakehouse.dim_customer` | `custkey`, `name`, `mktsegment`, `nationkey`, `acctbal`, `valid_from`, `valid_to`, `is_current` | 150 000 | 1,37 (1 файл) | PARQUET | ZSTD | нет | **SCD Type 2**: `valid_from`/`valid_to`/`is_current` считаются оконной `LEAD(loaded_at)`. Отброшены `address`, `phone`, `comment` — запросу не нужны, и за счёт этого 7,84 МБ Bronze сжались до 1,37 МБ (×5,7). Таблица читается целиком при джойне, партиции не нужны |
| `silver.lakehouse.large_orders` | `orderkey`, `total_quantity` | 57 | 0,001 (1 файл) | PARQUET | ZSTD | нет | Здесь материализован **подзапрос Q18**: 6 млн строк lineitem сворачиваются в 57 заказов. Главное архитектурное решение слоя — после него ни один верхний слой lineitem больше не читает, пересчёт витрины стоит миллисекунды вместо секунд |
| `silver.lakehouse.fact_order` | `orderkey`, `custkey`, `orderdate`, `totalprice`, `total_quantity` | 57 | 0,007 (7 файлов) | PARQUET | ZSTD | `year(orderdate)` | Факт сужен до крупных заказов. Партиционирование по году сохранено сознательно — схема готова к росту sfN, при котором крупных заказов станут тысячи, а отсечение по периоду заработает сразу. Цена сейчас — 7 крошечных файлов вместо одного (видно в колонке «файлов»); это осознанный размен на масштабируемость |

> **Про замеры Silver.** Числа выше — на момент сборки слоя (`./scripts/stats.sh` сразу после
> `sql/02_silver.sql`). После экспериментов части 2 (`UPDATE` на 150 000 строк в schema evolution,
> затем авария и откат в time travel) та же `dim_customer` занимает **2,97 МБ в 3 файлах**:
> Iceberg не перезаписывает файлы на месте, а добавляет новые и держит старые, пока снапшоты
> не истекут. Это и есть цена time travel, и её видно в байтах. Убирается штатно —
> `ALTER TABLE ... EXECUTE expire_snapshots`.


### Gold (витрина)

Бакет `gold`. Плоская денормализованная таблица — ответ на бизнес-вопрос без джойнов.

| Таблица | Колонки | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| `gold.lakehouse.large_volume_customer` | `name`, `custkey`, `orderkey`, `orderdate`, `totalprice`, `total_quantity` | 57 | 0,002 (1 файл) | PARQUET | ZSTD | нет | Ровно колонки вывода Q18. Клиент берётся в **актуальной** версии (`is_current = true`) — в этом смысл SCD Type 2: если клиента переименуют, витрина покажет новое имя, а история останется в Silver. Партиционирование витрины в 57 строк было бы чистым вредом: 7 партиций по 8 строк. Формат PARQUET, потому что BI-инструменты и Spark читают его без дополнительных драйверов |

Общее правило по всем слоям: **партиционируем только там, где у запроса есть предикат**,
по которому можно отсечь файлы. Партиция без предиката — это лишние файлы и распухшие метаданные.

## 5. Тесты производительности

Бенчмарк: `./scripts/bench.sh`, сырые числа — `results/bench.csv`, лог — `results/bench.log`.

**Что и как мерилось.** Таблица для замера — та же, что и самая тяжёлая в Bronze: полный
`tpch.sf1.lineitem`, 6 001 215 строк, все 16 колонок. Для каждой пары (формат, кодек) создаётся
отдельная таблица `bronze.lakehouse.bench_<формат>_<кодек>`, то есть Bronze честно пересоздаётся
на каждом кодеке.

- `write_ms` — время CTAS-записи из `tpch` в MinIO;
- `mb` — физический размер данных: `sum(file_size_in_bytes)` по `"<table>$files"` (байты в MinIO, не оценка);
- `agg1_ms` — свёртка всей таблицы: `GROUP BY orderkey HAVING sum(quantity) > 300` (читает 2 колонки из 16 — проверяет распаковку + column pruning);
- `agg2_ms` — широкий агрегат по мерам: `sum(extendedprice*(1-discount))`, `avg(quantity)`, `count(DISTINCT shipmode)`;
- время берётся из самого Trino — `date_diff('millisecond', created, "end")` по `system.runtime.queries` для конкретного запроса, найденного по уникальному комментарию-тегу. Так из замера выпадает старт JVM у CLI и `docker exec`;
- агрегации прогоняются 3 раза, берётся **минимум**; запись — один раз (поэтому `write_ms` шумнее).

### 5.1. Главное сравнение на Bronze: GZIP против ZSTD

| Сжатие на Bronze | Время запроса (agg1 / agg2) | Размер Bronze, МБ | Вывод |
|---|---|---|---|
| **GZIP** | 1347 мс / 1229 мс | **141,4** | Самый компактный результат во всём бенчмарке — на 2,4% меньше ZSTD. Но распаковка дорогая: агрегации в **2,5 и 1,9 раза медленнее** ZSTD. Запись — 41,4 с |
| **ZSTD** | **532 мс / 646 мс** | 144,9 | За 2,4% проигрыша в размере — более чем двукратный выигрыш в скорости чтения. Запись 59,2 с (самая медленная из сжатых parquet). **Выбран для всех слоёв**: слои читаются многократно, а пишутся один раз |

Вывод по этой паре: GZIP имеет смысл только для «холодного» архива, который почти не читают.
Для слоёв медальона, которые перечитываются при каждом пересчёте Silver и Gold, экономия
3,5 МБ не стоит лишней секунды на каждом запросе — поэтому в лабе везде ZSTD.

Строка `PARQUET / LZ4` — не пропуск, а зафиксированный отказ движка:

```
Query 20261012_125324_00139_6w7mb failed: Compression codec LZ4 not supported for Parquet
```

Скрипт бенчмарка такие случаи не роняет, а помечает в CSV как `WRITE_FAILED` и идёт дальше.
При этом **ORC с LZ4 работает** — поддержка кодеков зависит не от Iceberg, а от конкретного
writer'а в Trino; это надо проверять, а не предполагать.

### 5.3. Выводы из матрицы

1. **Сжатие экономит в 2,2–2,5 раза и почти ничего не стоит.** Parquet: 358,8 МБ без сжатия
   против 141,4 МБ с GZIP (×2,54). ORC: 431,6 → 148,6 МБ (×2,9). При этом запись без сжатия
   не быстрее: PARQUET/NONE писался 70,0 с — дольше всех, потому что в MinIO уходит в 2,5 раза
   больше байт, и бутылочным горлышком становится не процессор, а ввод-вывод. Хранить сырые
   данные несжатыми бессмысленно: платишь и местом, и временем.
2. **Строковый формат непригоден для аналитики.** AVRO проигрывает Parquet/ORC в 5–7 раз на
   агрегациях (2845–3609 мс против 394–782 мс) и вдвое по размеру. Причина архитектурная:
   AVRO хранит данные по строкам, поэтому `agg1` вынужден читать все 16 колонок, чтобы
   получить две, а колоночные кодировки (RLE, dictionary) к строкам не применяются.
   AVRO в Iceberg уместен для метаданных и стриминга, но не для слоёв медальона.
3. **ORC на этом профиле чуть быстрее Parquet, но Parquet выбран сознательно.** ORC/ZSTD пишется
   за 24,5 с против 59,2 с у PARQUET/ZSTD и агрегирует быстрее (395 против 532 мс). Тем не менее
   все слои сделаны в PARQUET, потому что приоритет — совместимость: Spark (§6.2) прочитал
   Parquet-таблицы Bronze без единой дополнительной настройки, а BI-инструменты и Python-стек
   (pandas, DuckDB, polars) работают с Parquet как с форматом по умолчанию. Разница в 30 секунд
   на разовой записи слоя не стоит риска несовместимости. На sf100 решение стоило бы пересмотреть.
4. **Кодек влияет на чтение сильнее, чем на размер.** Разброс по размеру между SNAPPY, GZIP и
   ZSTD — 141–211 МБ (в пределах ×1,5), а по времени агрегации — 394–1347 мс (×3,4).
   Поэтому выбирать кодек надо по профилю чтения, а не по таблице степеней сжатия.
5. **Честное ограничение замера.** `task.max-writer-count=2` даёт ровно 2 файла данных на
   таблицу, то есть параллелизм чтения ограничен двумя сплитами у всех вариантов одинаково.
   Абсолютные числа на другой машине будут другими; сравнимы они между собой, а не с чужими
   бенчмарками. Время записи измерено один раз на вариант и шумит заметнее агрегаций —
   видно по PARQUET/ZSTD (59,2 с) против ORC/ZSTD (24,5 с) при почти равном объёме вывода.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Ответ |
|---|---|
| **Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)?** | У обычной БД хранение и вычисления слиты в одном сервере: чтобы считать тяжёлый запрос, надо масштабировать весь сервер вместе с диском, а данные лежат во внутреннем проприетарном формате, доступном только самой БД. Lakehouse разрывает эту связку. **Хранение** — дешёвое объектное (MinIO/S3), платишь за гигабайты и не платишь за простой; **вычисления** — отдельные движки, которые можно выключить, заменить или запустить параллельно: в этой лабе один и тот же Bronze одновременно читают Trino и Spark (§6.2), и ни одна копия данных для этого не делалась. **Формат открытый** (Parquet + Iceberg), поэтому нет вендор-лока: данные переживут смену движка. При этом, в отличие от «просто data lake» (папка с файлами на S3), Iceberg-каталог добавляет то, за что обычно и держат БД: атомарные коммиты, снапшоты, эволюцию схемы, time travel. Практический масштаб из этой лабы: 6 млн строк агрегируются за 0,4–0,8 с на одном контейнере с heap 3,5 ГБ — такую таблицу можно и в Postgres положить, но на sf100 (600 млн строк) одиночный сервер уже не вытянет, а тут достаточно добавить воркеров к Trino, не трогая данные. |
| **Пример schema evolution на Silver: добавила/переименовала колонку — что произошло?** | Скрипт `sql/05_schema_evolution.sql`, лог — `results/schema_evolution.log`. Сделано два изменения на `silver.lakehouse.dim_customer` (150 000 строк): `ALTER TABLE ... ADD COLUMN segment_rank integer` и `ALTER TABLE ... RENAME COLUMN acctbal TO account_balance`. **Что произошло физически: ничего.** Обе операции затронули только метаданные каталога и выполнились мгновенно — ни один parquet-файл не перезаписан, снапшот не добавлен. Iceberg сопоставляет колонки файла и схемы по числовым **field-id**, а не по имени и не по позиции, поэтому после переименования старые файлы читаются правильно (`account_balance` отдаёт прежние значения: `Customer#000000001 → 711.56`), а у добавленной колонки в уже записанных строках честно возвращается `NULL`. Сравните с обычной БД, где `ADD COLUMN` с дефолтом переписывает таблицу. Новый снапшот появился только когда данные реально изменились — `UPDATE ... SET segment_rank = ...` на 150 000 строк: в `"dim_customer$snapshots"` добавилась запись `operation = overwrite`. |
| **Пример скрипта восстановления данных из снапшота (time travel)** | Скрипт `scripts/time_travel.sh`, лог — `results/time_travel.log`. Сценарий аварии: `UPDATE silver.lakehouse.dim_customer SET name = 'CORRUPTED'` испортил все 150 000 строк. Восстановление в два шага, оба — чистый SQL: <br>1. **Посмотреть «как было»** — `SELECT ... FROM dim_customer FOR VERSION AS OF 8322278133635945171` (id взят из `"dim_customer$snapshots"`): данные на месте, авария затронула только текущий снапшот. <br>2. **Откатить таблицу** — `CALL silver.system.rollback_to_snapshot('lakehouse', 'dim_customer', 8322278133635945171)`. После вызова `count(*) WHERE name = 'CORRUPTED'` снова равен **0**, имена восстановлены, строк по-прежнему 150 000. Плохой снапшот остаётся в истории (его файлы никто не удалял), но текущим состоянием таблицы снова стал хороший — то есть откат сам обратим, пока не выполнен `expire_snapshots`. Повторная сверка Gold после откатa дала `mismatched_rows = 0`. Важно: `rollback_to_snapshot` принимает `snapshot_id` только литералом, поэтому id сначала читается запросом, а потом подставляется — ради этого демо и сделано shell-скриптом, а не одним .sql-файлом. |

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбран именно он |
|---|---|
| **Apache Spark 3.5.6** (движок) | Из трёх предложенных вариантов (BI / движок / дата-каталог) выбран **движок**, и вот почему. BI-инструмент (Superset, Metabase) подключался бы к lakehouse **через Trino** по JDBC — то есть проверял бы работоспособность Trino, а не открытость самого lakehouse. Дата-каталог показал бы только метаданные. Spark же идёт **в тот же Iceberg REST Catalog напрямую** и сам читает файлы из MinIO, вообще не зная про Trino: это прямая проверка главного обещания архитектуры — что данные не заперты внутри одного движка. Почему именно Spark, а не Doris/StarRocks: ему достаточно двух jar-зависимостей (`iceberg-spark-runtime`, `iceberg-aws-bundle`) и он умеет Iceberg REST Catalog штатно, без отдельного сервиса-брокера; для моей задачи (батчевый пересчёт слоёв) это и есть целевой инструмент — Doris и StarRocks сильны в интерактивных дашбордах, чего в варианте 3 не требуется. |

**Скрипт развёртывания** — профильный сервис в том же `docker-compose.yml` (запускается по
требованию, в постоянном стеке не висит):

```yaml
  spark:
    image: spark:3.5.6-scala2.12-java17-python3-ubuntu
    profiles: ["tools"]
    environment:                      # креды MinIO для S3FileIO
      AWS_ACCESS_KEY_ID: minioadmin
      AWS_SECRET_ACCESS_KEY: minioadmin
      AWS_REGION: us-east-1
    volumes:
      - ./scripts:/opt/lab/scripts:ro
      - ./results:/opt/lab/results
    entrypoint: [""]
    depends_on: [lakekeeper]
```

Запуск — `./scripts/spark_bronze.sh`; ключевое в нём то, что Spark получает адрес **того же**
каталога и того же бакета, что и Trino:

```bash
docker compose run --rm -T spark /opt/spark/bin/spark-sql \
  --master "local[2]" --driver-memory 1500m \
  --conf spark.jars.ivy=/tmp/ivy \
  --packages "org.apache.iceberg:iceberg-spark-runtime-3.5_2.12:1.9.1,org.apache.iceberg:iceberg-aws-bundle:1.9.1" \
  --conf spark.sql.extensions=org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions \
  --conf spark.sql.catalog.bronze=org.apache.iceberg.spark.SparkCatalog \
  --conf spark.sql.catalog.bronze.type=rest \
  --conf spark.sql.catalog.bronze.uri=http://lakekeeper:8181/catalog \
  --conf spark.sql.catalog.bronze.warehouse=bronze \
  --conf spark.sql.catalog.bronze.io-impl=org.apache.iceberg.aws.s3.S3FileIO \
  --conf spark.sql.catalog.bronze.s3.endpoint=http://minio:9000 \
  --conf spark.sql.catalog.bronze.s3.path-style-access=true \
  -f /opt/lab/scripts/spark_bronze.sql
```

**Мои действия и что увидела** (полный вывод — `results/spark_bronze.log`):

1. `SHOW NAMESPACES IN bronze` → `lakehouse`; `SHOW TABLES IN bronze.lakehouse` → 14 таблиц:
   `raw_customer`, `raw_orders`, `raw_lineitem` и 11 бенчмарочных `bench_*`. Spark увидел всё,
   что создал Trino, — ни одна таблица не регистрировалась в Spark отдельно.
2. Сырые данные Bronze: `count(*) FROM bronze.lakehouse.raw_lineitem` → **6 001 215** строк,
   выборка первых строк отдаёт те же значения, что и Trino (`orderkey=1, linenumber=1,
   quantity=17.0, extendedprice=21168.23, shipdate=1996-03-13`).
3. Spark **самостоятельно посчитал подзапрос Q18** по Bronze:
   `GROUP BY orderkey HAVING sum(quantity) > 300` → **57** заказов. Ровно столько же, сколько
   получил Trino на Silver. Два независимых движка на одних файлах дали одинаковый ответ.
4. Spark прочитал и служебные таблицы Iceberg: `raw_lineitem.files` → 2 файла,
   151 946 437 байт (те же байты, что показал `stats.sh` через Trino); `raw_orders.snapshots` →
   история снапшотов; `raw_orders.partitions` → 7 партиций по годам с числом строк
   (227 089 / 226 645 / 227 597 / 228 637 / 228 626 / 227 783 / 133 623).

Попутно нашлась и починилась проблема развёртывания: в образе `spark` домашний каталог
пользователя недоступен для записи, и `--packages` падал с
`FileNotFoundException: /home/spark/.ivy2/cache/resolved-....xml`. Лечится `--conf spark.jars.ivy=/tmp/ivy`.

## 7. Выводы

Медальон — это не три папки, а три разных контракта: Bronze отвечает за то, что источник
воспроизводим (все колонки, append-only, `loaded_at`), Silver — за качество и историю
(чистка, `trim`, SCD Type 2), Gold — за ответ на конкретный вопрос. Главный выигрыш оказался
не в структуре, а в границе между слоями: вынеся подзапрос Q18 на Silver, я свела 6 001 215
строк lineitem к 57 заказам, и после этого пересчёт витрины стоит миллисекунды вместо секунд —
верхние слои тяжёлую таблицу больше не читают вообще. По хранению бенчмарк показал, что сжатие
не компромисс, а бесплатный выигрыш: PARQUET/NONE оказался и самым большим (358,8 МБ), и самым
медленным на запись (70,0 с), потому что узкое место — ввод-вывод в объектное хранилище, а не
процессор. ZSTD выбран вместо GZIP не потому, что компактнее (он на 2,4% крупнее), а потому,
что агрегации на нём в 2,5 раза быстрее, а слои читают многократно, а пишут один раз; AVRO
отвергнут по архитектурной причине — построчный формат лишает запрос column pruning и
проигрывает в 5–7 раз. Наконец, ценность именно lakehouse, а не просто файлов на S3,
подтвердилась на двух проверках: `ADD COLUMN` и `RENAME COLUMN` на Silver прошли как
изменение метаданных, не тронув ни одного parquet-файла, а испорченная `UPDATE`-ом таблица
на 150 000 строк полностью восстановилась одним `rollback_to_snapshot` — и тот же самый Bronze
без копирования данных прочитал второй движок, Spark, получив те же 57 заказов.
