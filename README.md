## 2. Как воспроизвести

```bash
./scripts/up.sh                       # 1. стек: MinIO + Postgres + Lakekeeper + Trino
./scripts/q.sh -f sql/00_schemas.sql  # 2. схемы в трёх каталогах
./scripts/q.sh -f sql/01_bronze.sql   # 3. Bronze: сырой TPC-H sf1
./scripts/q.sh -f sql/02_silver.sql   # 4. Silver: чистка, SCD2, предрасчёт
./scripts/q.sh -f sql/03_gold.sql     # 5. Gold: витрина Q18
./scripts/q.sh -f sql/04_validate.sql # 6. сверка витрины с эталонным Q18
./scripts/stats.sh                    # 7. размеры слоёв
./scripts/bench.sh                    # 8. бенчмарк форматов и кодеков
./scripts/q.sh -f sql/05_schema_evolution.sql  # 9. ADD/RENAME COLUMN без перезаписи файлов
./scripts/time_travel.sh              # 10. авария и откат на снапшот
./scripts/spark_bronze.sh             # 11. второй движок поверх Bronze
```

После бенчмарка в Bronze остаются 11 таблиц `bench_*` (~2,5 ГБ) — это физическое
подтверждение размеров из `results/bench.csv`. Убрать их: `./scripts/bench_clean.sh`.

Точки входа: MinIO — <http://localhost:9101> (`minioadmin`/`minioadmin`),
Lakekeeper UI — <http://localhost:8181/ui/>, Trino — <http://localhost:8080> (user `trino`, пароль пустой).

> Порт MinIO на хосте — **9100/9101**, а не 9000/9001: 9000 на машине был занят другим проектом.
> Внутри compose-сети сервисы общаются по именам (`minio:9000`, `lakekeeper:8181`), поэтому
> проброшенные порты нужны только человеку и DBeaver.

## 3. Методология

### 3.1. Почему именно такой стек

Lakehouse строится из трёх независимых слоёв ответственности, и каждый компонент
заменяем, потому что между ними — открытые протоколы (S3 API и Iceberg REST), а не
проприетарные интерфейсы:

- **MinIO** (форк Silo) — S3-совместимое объектное хранилище. Хранение отделено от вычислений:
  данные лежат в бакете, а движок можно выключить, заменить или запустить второй.
  Официальные образы `minio/minio` больше не раздаются бесплатно, поэтому используется
  свободный форк с теми же портами и переменными.
- **Postgres** — транзакционная БД для метаданных каталога. Коммит снапшота Iceberg должен быть
  атомарным; у файловой системы нет нужных гарантий, у Postgres есть.
- **Lakekeeper** — Iceberg REST Catalog. Единый реестр таблиц, снапшотов и схем для всех движков
  сразу: и Trino, и Spark видят одну и ту же таблицу в одном состоянии.
- **Trino** — MPP-движок SQL без собственного хранилища. Читает TPC-H и пишет Iceberg в один
  SQL-скрипт, умеет и ORC, и Parquet, и Avro — это и дало возможность сделать бенчмарк кодеков
  одним движком, без переписывания пайплайна.
- **Spark** — второй движок (часть 2, п. 6.2) как доказательство открытости формата.

### 3.2. Почему sf1

`tpch.sf1` даёт lineitem 6 001 215 строк (~750 МБ в «плоском» виде). Это:
- достаточно, чтобы разница кодеков была видна в десятках секунд и сотнях мегабайт, а не в шуме;
- мало, чтобы прогон всей лабы (включая 12 комбинаций формат×кодек) укладывался в минуты
  на одном узле Trino с heap 3,5 ГБ внутри Docker-VM на 8 ГБ;
- детерминировано: `tpch.sfN` при одном N выдаёт одинаковые строки, поэтому результат Q18
  воспроизводим и сверяем с эталоном.

Масштаб одинаковый на всех слоях.

### 3.3. Медальон под Q18

Бизнес-вопрос варианта 3: *клиенты и их заказы, в которых суммарное количество товара
больше 300; топ-100 по сумме заказа.*

```
tpch.sf1                 BRONZE (бакет bronze)          SILVER (бакет silver)              GOLD (бакет gold)
customer  ──────────►  raw_customer   (все колонки) ──► dim_customer  (SCD Type 2)  ──┐
orders    ──────────►  raw_orders     (все колонки) ──► fact_order    (крупные)  ────┼──► large_volume_customer
lineitem  ──────────►  raw_lineitem   (все колонки) ──► large_orders  (sum>300)  ────┘      (57 строк, топ-100)
```

- **Bronze** — «как пришло»: все колонки источника, никаких фильтров. Добавлена одна
  техническая колонка `loaded_at` — метка загрузки. Она и есть минимальное обогащение,
  без которого на Silver невозможен SCD Type 2 и аудит происхождения строки.
- **Silver** — очистка (отбрасываем `NULL`-ключи, неположительные `quantity`/`totalprice`),
  нормализация (`trim` строк), обогащение (история версий клиента: `valid_from`/`valid_to`/`is_current`)
  и сужение до нужных колонок. Здесь же материализуется подзапрос Q18: 6 млн строк lineitem
  сворачиваются в 57 «крупных» заказов, и дальше ни один слой lineitem больше не читает.
- **Gold** — плоская витрина ровно под вопрос: `name, custkey, orderkey, orderdate, totalprice,
  total_quantity`, 57 строк. Клиент берётся в актуальной версии (`is_current = true`).

### 3.4. Решения по форматам и партиционированию

| Таблица | Формат | Кодек | Партиционирование | Почему так |
|---|---|---|---|---|
| `bronze.raw_customer` | PARQUET | ZSTD | нет | 150 тыс. строк, 7,8 МБ — партиции дали бы только мелкие файлы |
| `bronze.raw_orders` | PARQUET | ZSTD | `year(orderdate)` | 1,5 млн строк, 7 естественных партиций 1992–1998; любой период-фильтр отсекает файлы по метаданным |
| `bronze.raw_lineitem` | PARQUET | ZSTD | **нет (осознанно)** | Q18 агрегирует lineitem целиком, фильтра по дате нет → pruning не сработал бы, а партиции добавили бы файлов и метаданных |
| `silver.dim_customer` | PARQUET | ZSTD | нет | 150 тыс. строк, читается целиком при джойне |
| `silver.large_orders` | PARQUET | ZSTD | нет | 57 строк |
| `silver.fact_order` | PARQUET | ZSTD | `year(orderdate)` | схема факта готова к росту: при sfN>1 отсечение по году сразу работает |
| `gold.large_volume_customer` | PARQUET | ZSTD | нет | витрина в 57 строк, партиционирование здесь — вред |

Общее правило: партиционируем только там, где у запроса есть предикат, по которому
можно отсечь файлы. Партиция без предиката — это лишние файлы и распухшие метаданные.

### 3.5. Как измерялось

- **Время** берётся не оболочкой, а из самого Trino: `date_diff('millisecond', created, "end")`
  по `system.runtime.queries` для конкретного запроса. Запрос помечается уникальным
  комментарием-тегом, по нему и находится. Так из замера выпадает старт JVM у CLI и `docker exec`.
- **Размер** — физический, из метаданных Iceberg: `sum(file_size_in_bytes)` по таблице `"<table>$files"`.
  Это именно байты в MinIO, а не оценка планировщика.
- **Агрегации** прогоняются `REPEATS=3` раза, берётся **минимум** — он меньше всего зашумлён
  фоновым GC и кэшем страниц ОС.
- Два разных агрегата: `agg1` — свёртка всей таблицы (`GROUP BY orderkey HAVING sum(quantity) > 300`,
  читает 2 колонки из 16, проверяет скорость распаковки и column pruning); `agg2` — широкий
  агрегат по мерам (`sum(extendedprice*(1-discount))`, `avg(quantity)`, `count(DISTINCT shipmode)`).

### 3.6. Корректность

`sql/04_validate.sql` сравнивает витрину Gold с эталонным Q18, выполненным напрямую по
`tpch.sf1`. Результат прогона: `gold_rows=57, ref_rows=57, mismatched_rows=0` — витрина,
собранная через три слоя, совпадает с эталоном строка-в-строку.

## 4. Результаты прогона

Витрина Gold: **57 строк**, совпадает с эталонным Q18 (`mismatched_rows = 0`).
Слои: Bronze 7 651 215 строк / 188,4 МБ, Silver 150 114 строк / 1,38 МБ на момент сборки
(2,97 МБ после экспериментов части 2 — накопились файлы снапшотов), Gold 57 строк / 2,3 КБ.

Бенчмарк на lineitem (6 001 215 строк), полная таблица — `results/bench.csv`:

| PARQUET | SNAPPY | 34,7 | 196,0 | 782 | 724 |
| PARQUET | GZIP | 41,4 | **141,4** | 1347 | 1229 |
| PARQUET | **ZSTD** | 59,2 | 144,9 | 532 | 646 |

| ORC | NONE | 33,0 | 431,6 | 604 | 942 |
| ORC | SNAPPY | 47,3 | 211,2 | **394** | 949 |
| ORC | GZIP (ZLIB) | 27,0 | 148,6 | 460 | **541** |
| ORC | ZSTD | **24,5** | 153,7 | 395 | 550 |

2,4%; AVRO непригоден для аналитики (построчный формат, нет column pruning). Разбор — в
[`отчет.md`](отчет.md), §5.

## 5. Воспроизводимость и известные ограничения

- Конфиг Trino прибит к машине на 8 ГБ Docker-VM (`-Xmx3500M`, `mem_limit: 5g`,
  `task.max-writer-count=2`). Без явного heap образ берёт 80% памяти VM и контейнер
  убивает OOM-killer (`exit 137`) на записи lineitem — это случилось в ходе работы и
  зафиксировано в комментарии к `etc/jvm.config`.
- `task.max-writer-count=2` означает 2 файла данных на неразбитую таблицу. На скорость
  агрегаций это влияет (параллелизм чтения ограничен числом файлов), поэтому сравнение
  кодеков корректно только между собой, при одинаковом числе писателей.
- Пароли в конфигах демонстрационные (`minioadmin`, `postgres`) — стек поднимается только
  локально и наружу не публикуется.
